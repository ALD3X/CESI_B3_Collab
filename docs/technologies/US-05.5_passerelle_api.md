# US-05.5 — Comparaison complémentaire : passerelle d'API (Spring Cloud Gateway et Kong)

> **Epic :** EPIC 05, Comparaison et démonstration de deux technologies applicatives (complément à US-05.1 à US-05.4)
> **Application :** [boutique de démonstration](../../README.md) · **Scénario :** [`tools/scenarios/passerelle.py`](../../tools/scenarios/passerelle.py) · **Mesures :** [`tools/scenarios/mesures.py`](../../tools/scenarios/mesures.py)
> **Entrées :** [US-03.1, composant EN-2](../architecture/US-03.1_composants_fonctionnels.md) · [US-03.2, architecture](../architecture/US-03.2_architecture_macroscopique.md) · [US-02.1, attributs de qualité](../qualite_devsecops/US-02.1_attributs_qualite.md) · [US-01.1, besoin](../cadrage/US-01.1_synthese_besoin.md)

**But :** choisir la technologie du composant **EN-2 « Passerelle d'entrée »**, le point d'accès unique de la plateforme. Son rôle est défini dans US-03.1 : *router les requêtes, vérifier le jeton d'identité, limiter le débit par client, journaliser les accès*. Les services métier étant écrits en **Spring Boot**, la question posée est :

> **La passerelle doit-elle être un service Spring de plus, qu'on code, ou un composant dédié, qu'on configure ?**

Ce domaine ne figure pas parmi les exemples de la consigne. Il complète la comparaison principale (bus d'événements, US-05.1 à US-05.4).

---

## 1. Technologies comparées

| | **Spring Cloud Gateway** | **Kong Gateway** |
|---|---|---|
| **Modèle** | Application Spring Boot réactive (WebFlux, Netty). Les règles s'écrivent en YAML et en Java | Passerelle construite sur NGINX et OpenResty (Lua). Les règles s'écrivent dans un fichier déclaratif et activent des **plugins** |
| **Éditeur** | Broadcom (projet Spring Cloud), licence Apache 2.0 | Kong Inc. Licence Apache 2.0 jusqu'à la 3.9, puis édition Enterprise (voir §4) |
| **Version testée** | Spring Boot 4.0.10, Spring Cloud 2025.1.5 (Gateway 5.0) | 3.9 (image officielle `kong:3.9`), mode **sans base de données** |
| **Briques ajoutées** | Spring Security (JWT), **Redis** (limitation de débit), Resilience4j (coupe-circuit, nouvelles tentatives) | Plugins intégrés `jwt` et `rate-limiting` |

**Protocole équitable :**
- les deux passerelles tournent **en même temps** dans la boutique, devant **les mêmes services** (identité, catalogue, commandes, notifications, expédition). Le front peut passer par l'une ou l'autre (`python tools/boutique.py passerelle kong`) ;
- **mêmes règles :** catalogue et connexion publics, commandes protégées par un JWT HS256 émis par le service identité (signature, expiration, émetteur), 10 requêtes par seconde sur les commandes ;
- mêmes ressources : chaque passerelle est limitée à **2 CPU et 512 Mio** ;
- même scénario automatisé (12 vérifications) et mêmes mesures.

## 2. Critères d'évaluation (fixés avant les démos)

| # | Critère | Poids | Justification par le contexte | Comment on le mesure |
|---|---|---|---|---|

## 3. Résultats mesurés sur la boutique

### 3.1 Scénario identique (`python tools/scenarios/passerelle.py spring|kong`, 27/11/2026)

| Étape | Spring Cloud Gateway | Kong 3.9 |
|---|---|---|
| 1. Routage : catalogue public, connexion, mes commandes avec jeton | OK (3/3) | OK (3/3) |
| 2. Jeton absent, falsifié ou expiré → 401 | OK (3/3) (401 sans détail) | OK (3/3) (message explicite : `Invalid signature`, `token expired`) |
| 3. Rafale de 30 requêtes par un membre → 429 | OK | |
| 3. Un **autre membre** juste après la rafale | **5/5 acceptées** | **0/5 acceptées** |
| 4. Service commandes arrêté : erreur rapide | **503 en 1,1 s**, message JSON lisible par le front | 504 en 2,2 s, texte technique |
| 4. Le catalogue reste disponible | OK | |
| 4. Rétablissement après redémarrage du service (~20 s de démarrage) | 27 s | 21 s |
| **Total** | **12/12** | **11/12** |

**Limitation par application et non par membre (Kong).** Le plugin `rate-limiting` de Kong OSS compte les requêtes par *consumer*, c'est-à-dire par **application cliente** (le site web), ou par IP, en-tête ou chemin. Tous les membres qui passent par le site partagent donc le même quota : la rafale d'un seul membre bloque tout le monde. Spring Cloud Gateway limite par défaut **par utilisateur authentifié** (le sujet du JWT). Avec Kong, il faudrait limiter sur un en-tête portant l'identité du membre, posé par un composant en amont. La limitation sur les attributs du jeton relève de l'édition Enterprise (à confirmer).

### 3.2 Pièges des réglages par défaut, rencontrés en construisant la boutique

Ces constats ne sont pas théoriques : chacun a provoqué une erreur réelle pendant nos essais, puis a été corrigé.

| Piège | Spring Cloud Gateway | Kong 3.9 | Correction appliquée |
|---|---|---|---|
| **Service arrêté** | Coupe-circuit : repli au bout d'**1 s** | **75 s** d'attente avant un 502 (60 s par tentative, 5 nouvelles tentatives) | Kong : `connect_timeout` 1 s, `read_timeout` 5 s, `retries` 1 |
| **Délai de réponse trop court** | Le délai par défaut (1 s) a renvoyé **503 alors que la commande était enregistrée** (premier envoi vers Kafka plus lent) : risque de **double commande** | Délai de lecture de 60 s par défaut | Spring : délai porté à 5 s (même valeur que Kong) |
| **Coupe-circuit trop long à se refermer** | Ouvert après une panne, il est resté fermé au trafic **60 s** alors que le service était revenu | Pas de coupe-circuit | Spring : nouvel essai au bout de 10 s |
| **Cache DNS** (conteneurs recréés, nouvelles IP) | Appels vers l'ancienne IP : **erreurs 500**. Réponse DNS négative lente : jusqu'à 4 s | **Requêtes `/api/commandes` envoyées vers un AUTRE service** pendant 56 s (ancienne IP réattribuée) : grave pour la sécurité, le jeton du membre part au mauvais destinataire | Cache DNS de 5 s des deux côtés, délai de requête DNS d'1 s pour Spring. Sur Kubernetes, l'IP stable des Services évite ce cas |
| **Redémarrage progressif sur Kubernetes** | 1 erreur 500 sur 148 requêtes : connexion réutilisée vers une instance en cours d'arrêt | *(non déployé sur Kubernetes)* | Délai `preStop` de 5 s sur les pods + nouvelle tentative sur les lectures du catalogue : **0 erreur sur 130 requêtes** |
| **Mémoire** | — | Un processus NGINX par cœur de l'**hôte** : **836 Mio** | `KONG_NGINX_WORKER_PROCESSES=2` |

> **Leçon pour la politique de qualité :** les deux produits fonctionnent, mais **aucun n'est sûr avec ses réglages par défaut**. Les délais, le cache DNS et le coupe-circuit doivent être des **paramètres revus en architecture** et vérifiés par un test de panne dans le pipeline.

### 3.3 Mesures (`python tools/scenarios/mesures.py`)

| Mesure | Spring Cloud Gateway | Kong 3.9 |
|---|---|---|
| Latence ajoutée, p50 / p95 | +1,7 ms / +0,9 ms | **≈ 0 ms** (dans la marge de mesure) |
| Mémoire après charge | 265 Mio (passerelle + Redis) | **186 Mio** |
| Taille des images | 192 Mio (passerelle + Redis) | **115 Mio** |
| Démarrage jusqu'à la première route servie | 5,9 s | **5,3 s** |
| Lignes de code et de configuration à maintenir | 195 (YAML, 2 classes Java, `pom.xml`) | **53** (un fichier `kong.yml`) |
| Conteneurs à exploiter | 2 (passerelle, Redis) | **1** |

> **Faits et hypothèses.** Mesures prises sur un poste de développement (Docker Desktop, Windows 11), avec le client sur l'hôte. Elles servent à **comparer**, pas à dimensionner la production. Les deux passerelles ajoutent une latence négligeable devant le temps de réponse d'un service métier.

### 3.4 Exploitation constatée

| | Spring Cloud Gateway | Kong 3.9 |
|---|---|---|
| Configuration | Versionnée avec le code, testée et analysée par le pipeline comme les autres services | Fichier déclaratif intégré à l'image. En mode sans base, l'API d'administration est **en lecture seule** (405 sur une écriture) : bon point pour le GitOps |
| Console | Aucune (métriques via Actuator) | **Kong Manager** : routes, services et plugins visibles |
| Secret JWT | Variable d'environnement (Secret Kubernetes) | En clair dans `kong.yml` : Kong OSS ne lit pas les variables d'environnement dans ce fichier |
| Sécurité des images | Bloquée par le scan tant que Spring Boot 3.4 était utilisé (failles critiques corrigées seulement en Spring Framework 7). Migration vers Spring Boot 4.0 | Image `kong:3.9` sans faille critique corrigeable au 27/11/2026 |

## 4. Forces, faiblesses et limites

### Spring Cloud Gateway

| Forces | Faiblesses | Limites |
|---|---|---|
| **Même technologie que les services** : un développeur Spring la maintient, la teste et la fait analyser par le pipeline | **Fonctions à assembler** : Spring Security, Redis, Resilience4j. 195 lignes contre 53 | **Redis obligatoire** pour la limitation de débit : un composant de plus à exploiter et à sécuriser |
| **Limitation par membre** (sujet du JWT), sans développement | Réglages par défaut du coupe-circuit inadaptés (1 s puis 60 s) | Pas de console d'administration. Les règles ne sont visibles que dans le code |
| **Coupe-circuit, repli et nouvelles tentatives** intégrés : erreur claire en 1 s | Erreurs 401 sans message par défaut | Suit le rythme des versions majeures de Spring (migration Boot 4 imposée par les failles de sécurité) |
| Licence Apache 2.0 active, logique sur mesure facile (filtres Java) | Latence ajoutée (environ 1,7 ms) et mémoire JVM | Toute logique sur mesure est du code Java : risque d'y glisser de la logique métier |

### Kong Gateway

| Forces | Faiblesses | Limites |
|---|---|---|
| **Fonctions prêtes à l'emploi** : JWT et limitation de débit en quelques lignes, plus de 50 plugins | **Réglages par défaut dangereux** : 75 s d'attente, cache DNS ayant envoyé des requêtes au mauvais service, un processus par cœur de l'hôte | **Limitation par application, pas par membre**, dans l'édition OSS |
| **Latence quasi nulle**, un seul conteneur, image légère | Nouvelle technologie pour l'équipe. Les plugins sur mesure s'écrivent en Lua (ou Go, JavaScript, Python) | **Avenir de l'édition libre incertain** : la 3.9 semble être la dernière version open source publiée, les suivantes ne sortant qu'en Enterprise (constat de la communauté, sans annonce officielle de Kong). Risque sur les **correctifs de sécurité** |
| Configuration déclarative, administration en lecture seule : adaptée au GitOps | Erreurs techniques renvoyées en texte brut | Pas de coupe-circuit dans l'édition OSS : seulement des délais, des nouvelles tentatives et des contrôles de santé |
| Console Kong Manager, messages d'erreur JWT explicites | Secret en clair dans le fichier de configuration | |

## 5. Notation pondérée

Notes de 1 (faible) à 5 (excellent). Les poids sont fixés au §2, avant les démos.

| Critère | Poids | Spring Cloud GW | Kong | Justification |
|---|---|---|---|---|
| G1 Sécurité des accès | ×3 | **5** | 3 | JWT équivalents. Limitation par membre avec Spring (5/5), quota partagé avec Kong (0/5). Mauvais routage constaté avec Kong |
| G2 Résilience | ×2 | **4** | 3 | Repli JSON en 1 s et coupe-circuit, mais réglages par défaut à corriger. Kong : 75 s par défaut, pas de coupe-circuit |
| G3 Prise en main par l'équipe | ×3 | **5** | 3 | Mêmes langage, outils, tests et pipeline que les services |
| G4 Effort de mise en place | ×2 | 3 | **5** | 195 contre 53 lignes, Redis à ajouter |
| G5 Empreinte et performance | ×1 | 3 | **5** | +1,7 ms contre ≈ 0 ms. 265 contre 186 Mio |
| G6 Exploitation | ×2 | 3 | **4** | 2 conteneurs sans console, contre 1 conteneur avec console et GitOps |
| G7 Pérennité et licence | ×2 | **5** | 2 | Apache 2.0 actif, contre une édition libre figée en 3.9 |
| **Total (sur 75)** | | **63** | **51** | |

**Analyse de sensibilité :** même si l'édition libre de Kong restait maintenue (G7 = 5) et que l'équipe comptait un profil d'exploitation à l'aise avec Kong (G3 = 4), Spring garderait l'avantage (63 contre 60). Kong ne passe devant qu'en ajoutant la limitation par membre de l'édition **Enterprise** (G1 = 5 : 66 contre 63), donc avec une **licence payante**. Le choix dépend surtout de **qui maintient la passerelle** et de **la licence**, pas de la performance.

## 6. Recommandation pour la Petite Maison de l'Épouvante

### Recommandation : Spring Cloud Gateway pour la passerelle EN-2 en V1

**Pourquoi, dans ce contexte précis :**
- **Équipe Spring Boot réduite (C-11) :** la passerelle est maintenue par les mêmes personnes, avec les mêmes outils et le même pipeline que les services. Il n'y a pas de seconde technologie à apprendre.
- **Sécurité forte (C-03) :** la limitation **par membre** protège les ventes flash et les festivals contre un robot ou un membre abusif, sans pénaliser les autres clients.
- **Fiabilité (US-02.1) :** coupe-circuit, réponse de repli et nouvelles tentatives intégrés. La panne d'un service se traduit par un message clair en 1 s.
- **Licence et coûts :** Apache 2.0 activement maintenue, sans dépendance à une édition commerciale.

**Conditions de mise en œuvre :**
1. **Redis managé hébergé dans l'UE**, en haute disponibilité.
2. **Délais, coupe-circuit et nouvelles tentatives réglés route par route** (valeurs de la boutique comme point de départ), et **test de panne automatisé** dans le pipeline.
3. **Jetons signés en RS256** par le composant d'identité (EN-3), vérifiés grâce à ses clés publiques (JWKS). Le secret partagé HS256 ne sert qu'à la démo.
4. **Au moins 2 instances** de la passerelle derrière l'Ingress controller de l'orchestrateur ([US-06.1](../environnement_tests/US-06.1_architecture_orchestrateur.md)), qui garde la terminaison TLS. C'est déjà le cas dans la démo Kubernetes de la boutique.
5. **Règle d'architecture :** aucune logique métier dans la passerelle, vérifiée en revue de code.

### Quand Kong deviendrait le bon choix

Cette recommandation **n'est pas universelle**. Kong deviendrait préférable si :
- la plateforme ouvre des **API à des partenaires externes** (distributeurs, festivals, éditeurs en V2/V3) et a besoin d'un portail développeur, de clés d'API et de quotas par partenaire. Le modèle « par consumer » est alors exactement le bon ;
- les services deviennent **multi-langages** : une passerelle neutre évite de lier l'entrée du système à Spring ;
- l'entreprise accepte une **licence Enterprise**, ou une alternative libre activement maintenue (comme Apache APISIX) est retenue.

> **Message pour la soutenance :** *« Les deux passerelles tournent en même temps devant notre boutique. Kong fait le travail en 53 lignes de configuration, contre 195 pour Spring. Mais quand un membre lance une rafale de commandes, Kong bloque aussi tous les autres, parce qu'il compte par application. Et avec ses réglages par défaut, il a fait attendre un client 75 secondes, puis envoyé des commandes au mauvais service après un redéploiement. Spring Cloud Gateway répond en une seconde, limite membre par membre et reste maintenu par notre équipe Spring. C'est notre choix pour la V1, avec une règle : aucun réglage par défaut n'est accepté sans test de panne. »*
